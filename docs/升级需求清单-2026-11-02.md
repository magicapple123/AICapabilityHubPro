## 3. 需求清单

> 每条格式：**问题 → 方案 → 涉及 → 验收**。工期为单人估算，仅供排期参考。

### A. 并发与性能

#### A1　模型调用移出事务（最高优先级）

- **问题**：`chat_service.complete()` 中，数据库连接从 `_prepare_session` 一直持有到最后的 `db.commit()`，中间包含 3–10 秒的模型调用。连接池 15 个 ÷ 5 秒 ≈ **3 QPS 上限**，而网关给 ai-chat 的限流是 20 QPS。
- **方案**：改为 `commit 用户消息 → 调用模型 → 开新事务写助手消息与账单`。模型失败时用户消息已提交，需定义失败标记（会话状态或占位消息），不得静默丢失。
- **涉及**：`ai-chat-service/app/service/chat_service.py`、`conversation_store.py`
- **验收**：mock 模式下压测，单进程吞吐从约 3 QPS 提升到 30+ QPS；模型失败的用例仍能查到用户消息与失败记录。
- **工期**：1 天　**风险**：低

#### A2　连接池参数化 + 多 worker

- **问题**：`pool_size=5 / max_overflow=10` 写死在四个服务的 `app/db/session.py`。
- **方案**：改为环境变量；启动加 uvicorn 多 worker。**必须同步把 MySQL `max_connections` 调到 ≥300**（4 服务 × 4 worker × 15 = 240，默认 151 会直接连挂）。
- **验收**：4 worker 下并发扣分测试仍不超扣；`SHOW STATUS LIKE 'Threads_connected'` 不触顶。
- **工期**：0.5 天　**风险**：低

#### A3　目录读取优化

- **问题**：每次执行都有 1 次 capability 内部调用 + 4 次串行跨服务调用。
- **方案**：目录加短 TTL 缓存（1–5 秒）+ 事件失效；预检与扣分合并为一次调用。**这是"正确性换吞吐"的取舍，必须在文档里写明**——当前是不缓存以保证改价立刻生效。
- **验收**：改价后 ≤5 秒生效；缓存命中率与 P95 延迟有指标可看。
- **工期**：1.5 天　**风险**：中

#### A4　按用户限流

- **问题**：只有网关的服务级 QPS 限流（chat 20 QPS），单个用户可以打满。
- **方案**：服务内内存令牌桶（如单用户 10 QPS），超限 4001。
- **验收**：单用户高频请求被限，其他用户不受影响。
- **工期**：0.5 天　**风险**：低
- **备注**：多实例下内存桶不准，需在文档标注为已知限制。

#### A5　压测三轮 + 报告

- **方案**：① `USE_MOCK=true` 只打 chat，测平台极限 ② 真实模型低速递增 5→10→20 QPS，找 p95 与 429 拐点 ③ 读接口基线 60 秒。
- **红线**：**压测客户端不得与被压服务同机**（CPU 互抢会失真）；高 QPS 用 wrk/hey 或多进程 locust。
- **产出**：`docs/压测报告-<日期>.md`，写清场景口径。
- **工期**：0.5 天

### B. 可观测与运维

#### B1　审计日志

- **问题**：全库无审计表。运营改价、上下架、调分、禁用账号均无痕迹。
- **方案**：新增 `t_operation_log`（operator_id / resource_type / resource_id / action / before_json / after_json / request_id / create_time）。在 capability 的增改删、状态变更、分类写操作、用户管理写操作处埋点；新增查询接口 + 运营后台列表页。
- **约束**：**应用层只允许追加，不提供更新与删除接口**。用户数据导出、调分、禁用等敏感操作本身也要写一条。
- **验收**：改价后能查到操作人、时间、改前改后；无法通过任何接口修改历史记录。
- **工期**：1.5 天　**风险**：低

#### B2　readiness 健康检查

- **问题**：四服务 `/ping` 是占位接口（只回 pong + 身份），DB 挂了仍返回 200。
- **方案**：新增 `/health/ready`，检查 DB `SELECT 1` 与必要依赖；失败返回 503 + 原因码。**保留 `/ping` 不变**（契约兼容）。
- **验收**：停 MySQL 后 ready 变 503，恢复后自动回 200。
- **工期**：0.5 天　**风险**：低

#### B3　Prometheus 指标

- **方案**：接 `prometheus_client`，暴露 `/metrics`。至少包含：HTTP 请求数/错误数（按 service+route+code）、模型调用耗时直方图、扣分成功/失败计数、目录查询失败计数、**连接池 checkout 等待**、**按 provider 拆分的上游错误率**。
- **验收**：压测时能采集，报告可引用 p95。
- **工期**：1 天　**风险**：低

#### B4　自动对账任务

- **问题**："按 requestId 对账"只写在文档里，没有代码。
- **方案**：定时任务扫描 billing 账单与 user 积分流水，找出「有账单无流水」「有流水无账单」「requestId 不一致」三类差异，输出报告，支持手动触发。**必须幂等可重跑**，不产生重复告警。
- **验收**：构造一条不一致数据能被检出；连续跑两次不重复报警。
- **工期**：1 天　**风险**：中

#### B5　runbook + 交付验收脚本

- **方案**：runbook 覆盖 DB 不可用、Nacos 不可用、模型 401/429、磁盘满、服务起不来五类，每类给「症状 → 三步处置 → 升级路径」；验收脚本依次跑健康检查、登录、一次真实调用、查收据、查记录，输出通过/不通过。
- **工期**：1 天

### C. 计费与计量

#### C1　修正 token 用量（前置，必须先做）

- **问题**：`completion_result` 中 `prompt_tokens = sum(len(content))` 是**字符数**，`completion_tokens` 取上游 `total_tokens`，两者不可比，不能用于计费。
- **方案**：改为读取上游返回的 `usage.prompt_tokens` / `usage.completion_tokens` 落库；Responses 协议用 `input_tokens` / `output_tokens`，需归一化。
- **涉及**：`ai-chat-service/app/service/completion_result.py`、`model_client.py`、`billing` 收据字段、契约文档、E2E 断言
- **验收**：一次调用的 token 数与上游控制台一致（允许 ±1）。
- **工期**：1 天　**风险**：中（波及契约与测试）

#### C2　双轨计费

- **方案**：能力表加 `billing_mode`(`per_call` / `per_token` / `per_unit`)、`price_per_1k_input`、`price_per_1k_output`、`price_per_unit`、`unit`。**旧的两个能力保持 `per_call` 不变**，新能力可用 token 或按张。
  - `per_token` 模式下预检无法预知 token 数 → 改为**最低余额门槛**（至少够 1k token）
  - 结算按实际 usage 向上取整
  - 收据展示 token 明细
- **待定**：积分与 token 的换算比例（建议 1000 tokens = 1 积分，需写入契约并定标）
- **验收**：一次 4,050 tokens 的调用按约定比例扣分；旧能力扣分金额不变。
- **工期**：2.5 天　**风险**：中

#### C3　预算上限

- **问题**：按 token 计费后，agent 一次任务几十轮，QPS 限流限不住成本。
- **方案**：用户与 API Key 的日积分上限；扣分前校验当日已消耗（聚合 `t_usage_daily` 或 `points_log`）；超限返回**新增的 3003**（不要复用 3002 幂等冲突）。
- **验收**：设 50 分/日，跑满后下一次返回 3003，且不产生账单。
- **工期**：1 天

### D. 能力与上游

#### D1　上游供应商表 + 密钥管理

- **问题**：目前所有能力共用一份全局配置（`MODEL_BASE_URL` / `MODEL_API_KEY` / `MODEL_NAME`），能力表没有模型字段。
- **方案**：新增 `t_model_provider`，**放在 ai_chat_db**（Key 不跨服务传）：
  `name` / `protocol`(openai-chat|openai-image|openai-embedding|custom-http) / `base_url` / `api_key_cipher`(AES-256-GCM) + `api_key_mask` / `default_model` / `timeout_ms` / `extra_json` / `status`
- **安全策略（已定）**：
  1. 白名单：后台维护允许域名，不在表里直接保存失败
  2. 禁内网：请求前 DNS 解析，拒绝 `10/8`、`172.16–31`、`192.168/16`、`127/8`、`169.254/16`（云元数据）、`::1`、`fc00::/7`
  3. 禁跟随重定向、只允许 https、防 DNS 重绑定（锁定已校验 IP）
  4. 连通性测试：**允许存草稿，「启用」前必须测通**
- **工期**：2 天（含安全校验）　**风险**：中高

#### D2　执行器抽象（code / executor 解耦）

- **问题**：`code` 同时兼任"能力编码"与"执行器选择"（`SUPPORTED_CODES`），导致新能力必须改代码才能跑。
- **方案**：
  - 能力表加 `executor`（chat|summary|image-generate|embedding）与 `provider_alias`（字符串，跨库不建外键）
  - `Executor` 协议：`code` / `input_model` / `supported_protocols` / `execute(definition, provider, payload, runtime)`
  - 绑定校验前置：`image-generate` 只能绑 `openai-image`，保存阶段就拒绝
  - `prepare_execution` 与市场「暂无执行器」判断改为 `executor in EXECUTORS`
- **波及面（重要）**：市场无执行器判断、OpenAI 兼容层 model 映射、内部详情接口、369 项测试、契约文档——**必须同步改，否则大面积红**
- **工期**：1.5 天　**风险**：高

#### D3　文生图执行器

- **方案**：上游 `/v1/images/generations`；入参 `prompt / size / n / style`；出参 URL 或 b64；provider 级超时 60s；按 `per_unit`（张）计费。
- **产物存储（已定）**：**本地磁盘**，下载后存本地目录，库里记相对路径，Nginx 托管（生产再换对象存储）。
- **前端**：调试台结果区加图片渲染分支；调用记录可预览。
- **工期**：3 天　**风险**：中

#### D4　上游参数与容错

- **问题**：上游请求体只发 `model/messages/temperature/max_tokens(固定1024)/stream=false`；429/402/超时全部归到 5001/5002。
- **方案**：
  1. 参数白名单透传：`top_p` / `stop` / `seed` / `response_format` / `presence_penalty` / `frequency_penalty` / `logprobs`；**保留 `extra="forbid"`**，未列入白名单的字段照旧拒绝
  2. `max_tokens` 按能力配置：能力表加 `max_output_tokens`，请求值取 `min(请求值, 能力配置)`
  3. 错误码细分：`5003` 限流(429) / `5004` 鉴权欠费(401/402) / `5005` 上游故障(5xx)
  4. 重试 + 熔断：仅对超时与 5xx 重试一次（退避 300ms），4xx 不重试；**红线：重试与熔断都不得产生第二条账单或第二次扣分**
- **工期**：2.5 天

#### D5　上架体验与目录语义

- **上架体验**：登记表单实时提示「该编码已有执行器 / 暂无执行器」（复用 `/api/chat/executors`）；提供 Schema 模板（聊天 / 摘要 / 自定义）
- **版本回滚**：基于审计日志的 before/after，提供「回滚到此版本」，回滚动作本身也写审计
- **分类停用语义**：市场查询加 `category.status='enabled'` 条件（现状只过滤 `is_deleted`，停用分类后其能力仍可见）
- **软删 code 复用**：唯一索引 `(code, is_deleted)` 导致同一 code 二次软删冲突 → 新增生成列 `active_code = IF(is_deleted=0, code, NULL)` 并对其建唯一索引（MySQL 8 下 NULL 不参与唯一约束）
- **工期**：2.5 天

### E. Agent 接入（员工用 AI 写代码）

> 目标：员工拿 API Key 在自己常用的编程客户端里调用平台能力，走同一条计量链。
> **范围：只做 OpenAI 协议**（`/v1/chat/completions` + `/v1/responses`）。Anthropic `/v1/messages` 与 Claude Code 移入未来计划。

#### E1　真流式 SSE

- **问题**：现在兼容层是"伪流式"——先算完再一次性吐一个 chunk。
- **方案**：流期间不持有 DB 连接、不结算；流结束后记账；逐块转发上游。
- **待定**：客户端中途断开的计费规则（按已生成部分 / 不计费）
- **工期**：1.5 天

#### E2　工具调用

- **方案**：`ChatMessage.role` 加 `tool`；assistant 消息支持 `tool_calls`；透传 `tools` / `tool_choice`；解析上游 `tool_calls` 并回传；能力 Schema 支持描述 tools。
- **计量口径（已定）**：**每轮单独计费**。
- **工期**：3 天　**风险**：中高

#### E3　OpenAI `/v1/responses`

- **依赖**：E2（工具调用做成内部统一能力，两个端点只做协议翻译）
- **支持**：`input`（字符串或 items）、`instructions`、`tools`（function）、`stream`、`usage`
- **明确不支持**：`previous_response_id`、`store`、内置工具（web_search / file_search）、`reasoning` items、background 模式——**收到应返回明确的 4001，不静默忽略**
- **事件翻译**：`response.created` → `output_item.added` → `content_part.added` → `output_text.delta` → `output_text.done` → `output_item.done` → `response.completed`
- **网关**：无需改动，`Path=/v1/**` 已覆盖，限流沿用 20 QPS
- **验收客户端**：Codex CLI 设 `model_provider.base_url` 与 `wire_api="responses"`，**锁定一个 CLI 版本**做回归
- **工期**：3.5 天　**风险**：高（规范仍在演进）

#### E4　模型服务视图

- **方案**：运营后台新增「模型服务」页签，agent 类能力只需 4 个字段（名称 / 模型 / 计价 / 状态）；能力表加 `exposed_to_market`，市场只展示 `1` 的能力，模型服务不进市场、不用调试台。
- **工期**：1 天

### F. 管理与安全

#### F1　管理员用户管理 + 跨用户流水

- **方案**：
  - user-service：`GET /api/user/admin/users`（分页/状态/关键词）、`GET .../{id}`、`PUT .../{id}/status`、`POST .../{id}/points`；权限复用 `require_admin` 实时校验，失败关闭
  - billing-service：`GET /api/billing/admin/records?user_id=&start=&end=&status=`、`GET /api/billing/admin/users/{id}/usage`
  - 前端：运营后台「用户管理」tab（列表 → 详情抽屉：余额、用量趋势、最近调用、Key 列表 → 禁用/启用、调整积分）
- **边界（已定）**：
  1. **不给会话正文**，管理员只看元数据；正文不出 ai-chat，也不进审计
  2. 调分必填原因、单次上限 ±10000、写 points_log + 审计、余额不得为负
  3. 支持 CSV 导出（用户列表 + 用量明细），复用现有 `exportRecords`
- **验收**：普通用户访问 admin 接口被拒；禁用后下一次调用 1005 且不能再登录；调分后余额与流水一致；导出与页面筛选一致
- **工期**：5 天

#### F2　双密钥轮换

- **方案**：JWT 增加 `kid` 版本，验签时依次尝试所有 active key；provider 主密钥密文带版本前缀（如 `v2:base64`），解密按版本选 key。
- **验收**：新旧密钥并存期间两边的 token 都能通过。
- **工期**：0.5 天

#### F3　依赖锁定

- **问题**：`requirements.txt` 是范围约束（`fastapi>=0.115,<1.0`），构建不可复现。
- **方案**：用 pip-compile/uv 生成 lock，CI 用 lock 安装。
- **工期**：0.5 天

#### F4　备份与恢复

- **问题**：`scripts/` 下无任何备份/恢复脚本，也没做过恢复演练。

## 8. 自主执行协议

> 本节是给自动执行的约束。目标是「不停下等人、也不自己给自己放水」。

### 8.1 执行循环（逐条）

1. **读代码确认现状**——不要相信文档里的文件名和行号，它们会过期
2. 若代码与文档冲突 → 记入实施日志，**以代码为准**
3. 设计最小改动方案；涉及接口/字段变更的，**先改 `docs/api-contract/` 契约文档**，再改代码
4. 实现 + 同步补测试（不得只改实现不补测试）
5. 跑该批的门禁命令（第 4 节表里那一列）
6. **全绿** → 日志打勾，进入下一条
7. **不绿** → 修复，最多 3 轮（见 8.3）

### 8.2 验收门禁（必须客观可执行）

**必须真的执行命令并保留输出**，不接受"看起来没问题""逻辑上是通的"这类主观判断。

| 门禁项 | 要求 |
|---|---|
| 单元/集成测试 | 对应服务 pytest 全绿，**测试数量不得减少** |
| 数据库测试 | 必须连隔离实例，禁止连开发库或演示库 |
| 契约一致性 | `python scripts/contract_lint.py` 通过；接口字段有变必须同步契约文档 |
| 网关 | `mvn -q -f gateway/pom.xml test` 通过 |
| 前端 | `pnpm --dir web lint` 与 `pnpm --dir web build` 通过 |
| 工具与冒烟 | `python -m pytest tests/tooling -q`、`python scripts/smoke_check.py` |
| 文档 | 新增的表/字段/错误码/接口必须写进对应契约文档 |

**两条防自欺规定**：

- 门禁结果必须来自**本次实际执行**。上下文被压缩后必须重跑，不得以"之前跑过是绿的"为由跳过。
- 失败用例要贴出用例名，不能只写"有测试失败"。

### 8.3 自动返工规则

- 门禁失败 → 自行定位并修复，**最多 3 轮**
- 3 轮内修好 → 继续下一条
- 3 轮仍失败 → 在实施日志标记 **⛔ 受阻**，写明「现象 / 已尝试的 3 种方案 / 怀疑根因」，**跳过该条继续下一条**，不要阻塞全局
- **禁止为了让构建变绿而**：删测试、降低断言强度、加 `skip`/`xfail`、跳过 CI 检查、把异常吞掉

### 8.4 并行与子团队规则

**可以并行，但有三条硬约束**：

1. **同一文件同一时间只能有一个执行者**。并行前先划分文件所有权。
2. **依赖链不可并行**：`D1 provider → D2 执行器抽象 → D3 文生图 / E2 工具调用 / E3 Responses`。上游没落地，下游不要开工。
3. **先冻结契约再并行**：表结构、接口字段、错误码先在日志里定死，否则两条并行线会互相踩。

**建议的子团队分工**：

| 角色 | 职责 | 时序 |
|---|---|---|
| 架构师 | 定表结构、接口字段、错误码、执行器抽象形态 | 每个批次开始前，一次性产出「本批契约冻结清单」 |
| 工程师 | 按冻结的契约实现 | 契约冻结后并行 |
| QA | 按验收条目写测试，并在工程师交付后跑门禁 | 与工程师交叉，但测试文件独立 |

主代理负责：拆分任务、划分文件所有权、合并、跑门禁、写日志。**不要让两个执行者同时改同一个文件**。

### 8.5 进度日志与压缩恢复（必须做）

自动压缩会丢细节：改过哪些文件、为什么这么改、试过什么方案失败——**这些被压缩掉就再也想不起来**。所以日志不是备份，是唯一事实源。

**维护 `docs/升级实施日志.md`**，每完成一条立刻追加，不要攒到最后：

| 字段 | 必须写什么 |
|---|---|
| 编号 | 如 C1 / D2 |
| 状态 | ⬜ 未开始 / 🟡 进行中 / ✅ 完成 / ⛔ 受阻 |
| 改动文件 | **逐个列全路径**——压缩后靠这个才知道动过什么 |
| 关键决策 | 为什么这么改，一句话（例：改事务边界而非换异步 ORM，因为回归面小） |
| 门禁结果 | 跑了什么命令、绿还是红、失败的用例名 |
| 新增契约 | 新表 / 新字段 / 新错误码 / 新接口 |
| 失败尝试 | 试过但没用的方案——防止压缩后重走同一条死路 |

同时维护一张**当前文件所有权表**（并行开发时用），记录每个文件当前归谁改，压缩后用它恢复并行分工。

**上下文被压缩后，第一件事不是继续写代码，而是三件事对齐**：

1. 读实施日志，确认最后一个 🟡 是什么、动过哪些文件
2. 用 `git status` / `git diff --stat` 核对磁盘上实际改了什么，与日志逐项比对
3. 重跑该条的测试，确认"日志说改完了"与"代码真的改完了"一致

三者对齐后，才继续下一条。**不要凭记忆继续**——压缩后的记忆最危险的失真，是把"计划要改"记成"已经改完"。

4. 同一批次连续 3 条 ⛔ 受阻
