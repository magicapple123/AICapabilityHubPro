## 实施与验证顺序

1. Gateway 可信头/JWT/白名单/限流：`mvn -q test`。
2. 会话持久化单独提取后先跑原服务测试，再接入能力查询与执行器。
3. ai-chat：在专用 MySQL 中执行原测试和新增失败场景；JUnit 必须零 skipped、failure、error。
4. 前端：纯输入测试 → `pnpm lint` → `pnpm build`，再做实际浏览器联调。
5. 集成：使用独立数据库和不同端口启动真实 user/capability/billing/ai-chat/Gateway；分别验证聊天 5 分、摘要 3 分、真实账单/积分/requestId 一致及不足积分等负例。
6. CI：网关、四服务、Web 和公共门禁；新增 E2E 工作流。交付前扫描模块行数并归档结果。

## 依赖交接与兼容边界

- `GET /internal/capability/{id}` 仍由夏思凯实现；默认内部模式在其缺失/错误/不可达时失败关闭。显式 `CAPABILITY_CATALOG_MODE=market` 可读取已有公开市场详情，只有服务确认已上架的能力可执行；不自动从失败的内部接口退回市场模式。
- API Key 兑换端点冻结为 `POST /api/user/apikeys/exchange`；Gateway 实现白名单/限流/禁止缓存，凭证验证和 TTL 由黄禹菲完成。
- role 只从验证签名后的 JWT 读取，用于可信转发；管理实时授权仍由 user/capability/billing 负责人实现。
- 旧 billing 已接受 `capability_id` 和 `points`，组长传入目录 ID 与登记价，保留全链路 requestId；其新增价格字段、管理员统计保护及迁移留给负责人。
- 不宣称跨服务事务原子性。billing 成功而 ai-chat 最终提交失败时，须用同一 requestId 对账；本轮不引入分布式事务或盲目自动重试模型。
- 正式发布 Tag 以三人功能和 Review 通过为前提。本轮交付可审查的组长业务 PR 与演示/验收工具，不把未完成的成员业务发布为最终版。
