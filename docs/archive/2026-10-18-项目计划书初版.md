## 一、项目摘要

小组还剩三周，本次目标是在已有 AI 能力开放平台上完成一轮有辨识度的升级，而不是重复搭建已完成的网关、用户服务、计费服务和前端。最终版要能清楚展示“平台能力目录 → 选择能力 → 安全调用 → 按能力价格计费 → 查询调用结果”的业务闭环，同时补上普通用户与管理员的权限边界，并提供真实可运行的 API Key 使用流程。

### 与旧项目相比，本次明确新增或强化的功能

1. **能力市场一键体验与受控动态分发**：用户从市场选中具体能力后进入对应输入表单；后端按能力 ID 获取最新上架状态、参数 Schema 和登记单价，再分派至代码中明确允许的执行器。旧版目录与聊天接口之间缺少这条完整链路。
2. **Schema 驱动的调用与费用预览**：调试页展示该能力要求的参数、每次积分价格和执行状态；提交前能看清实际调用对象与费用。后端仍需再次校验，前端预览不构成安全控制。
3. **API Key 兑换短期访问 Token**：API Key 不再只是可创建、可展示的管理项，开发者可以使用 access key 和 secret key 兑换短期 JWT，并用 JWT 访问平台 API。secret 仅创建时显示，不能写入日志或明文保存。
4. **开发者与管理员双角色治理**：管理员才能变更能力状态、维护目录和查看全局运营统计；普通用户仍可使用公开能力、查询自己的积分和调用记录。
5. **按能力单价的调用计量**：能力登记价格、AI 服务预检、积分扣减和调用账单中的 capability ID/费用必须一致，取代旧版 AI 服务独立固定积分配置的演示方式。
6. **可核对的调用追踪**：在调试界面和个人调用记录中展示能力、状态、积分和 requestId，使现场演示能说明一次请求经过了哪些服务以及扣费结果。

三周时间内不建设任意插件执行平台；数据库中的 service name/path 不能直接作为任意 URL 执行。本轮仅允许通过安全评审和测试的聊天与文本摘要适配器执行。视觉能力或其它未实现能力应标为暂不可体验。

## 三、目标与范围

### 3.1 三周内必须完成（P0）

1. **用户角色和服务端授权**：普通用户注册默认 role=user，不能自助改成 admin；admin 可进行能力管理和查看全局统计；普通用户访问相同 API 必须得到统一拒绝响应。管理授权依赖当前用户数据，不只相信长期或过期 JWT 中的 role。
2. **市场到调用的完整闭环**：从已上架能力详情取得 Schema 和价格；服务端校验状态、受支持 code 和请求内容；按登记价格预检积分、生成正确的能力调用记录并扣分。能力不存在、下架或暂不支持时必须在模型调用前拒绝。
3. **至少一项可完整演示的 AI 能力，目标两项**：聊天能力为 P0；文本摘要是目标 P0。D8 设 Go/No-Go：摘要若届时未通过参数 Schema、实际 adapter、Mock、计费和端到端检查，就转为 P1，不对用户显示为可体验。视觉理解不纳入本轮。
4. **API Key 兑换短期 JWT**：创建 Key 时 secret 明文仅返回一次；有效 Key 可以换 JWT；错误、已禁用、过期的 Key 不能换 Token。不得在数据库或日志存明文 secret。
5. **新功能前端入口**：市场有“体验该能力”入口；调试台显示 Schema 对应输入项、登记积分价格、调用状态和 requestId；开发者设置页支持创建 Key、一次性查看与兑换说明；管理页有清楚角色权限差异。
6. **真实登录和旧数据库迁移说明**：Vite 默认关闭 Mock 登录；README 写明干净环境启动和已有数据库升级步骤；SQL 迁移可重复执行且不丢已有业务数据。
7. **自动化和现场回归**：Gateway Maven 测试、各 Python 服务 pytest、Web lint/build 和端到端主链路均需真实运行并记录结果；至少覆盖未登录、普通用户越权、Key 过期/禁用、能力下架、初始积分不足、模型降级等负向分支。

### 3.2 本期明确不做

- 真实支付/充值/退款、消息队列、Redis、Kubernetes、分布式事务、SSE 流式响应、模型训练或微调、视觉/视频处理。
- 任意第三方服务自动接入或任意 URL/服务路径代理；不安全地把能力表的 service/path 当作可执行指令。
- 多租户组织、复杂角色树、公开 SaaS 部署、供应商路由或企业级密钥管理。
- 清空/删除原项目、重置 Git 历史、删除旧数据库数据卷，或将“删库重建”作为唯一部署方法。

### 3.3 验收定义（DoD）

- 新环境能按 Pro README 启动；已有 MySQL 环境按增量迁移步骤升级，原数据保留。
- 伪造 X-User-* 或 role 头不能提升身份；普通用户访问管理 API 被拒绝；授权依赖不可用时管理操作失败关闭。
- 市场所选能力 ID 到模型 adapter、扣分流水和调用记录保持一致。登记价、账单 cost 和用户积分变化能相互核对。
- 对初始余额不足用例，模型调用次数为 0，且无成功扣款/计费记录；重复相同幂等 requestId 不会重复扣分。
- API Key 的 secret 在创建响应中只出现一次；有效 Key 换取有时长上限的 JWT；失效 Key 不能换 Token。
- 自动化测试与手动 E2E 结果可复现；不得删测、跳测、放宽断言来制造通过。
- 三人可在 8–12 分钟内完成核心演示和至少三种异常分支；已知的跨服务非原子边界如实记录。

## 四、业务链路与接口原则

### 4.1 目标调用链

1. 开发者登录，或 POST 提交 access key 和 secret key 换取短期 JWT。
2. 浏览能力市场，选择 capability ID；页面展示该能力 Schema、可体验状态和 price_per_call。
3. Web 向 Gateway 发送能力 ID 与输入。Gateway 验证 JWT、清理客户端伪造的身份头、生成/传递可信 requestId。
4. ai-chat-service 向 capability-service 内部接口读取该能力的最新上架状态、受控 code、Schema 和价格。
5. AI 服务检查 allowlist 和输入 Schema；再向 user-service 检查用户状态及当前余额是否满足该能力价格。
6. 只对实现且登记允许的聊天/摘要 adapter 执行 Mock 或本地配置的真实模型。
7. ai-chat-service 向 billing-service 记账，传递同一用户、能力 ID、实际价格、状态、耗时和 requestId；billing 按既有幂等机制调用 user-service 扣分。
8. 前端显示回复和结果；个人调用记录可查询能力、积分、状态和 requestId；admin 侧运营列表显示真实汇总。

### 4.2 接口兼容与安全

- 保留原 POST /api/chat/completions；请求增加 capability_id 和与所选能力相符的输入。D2 前冻结字段名、Schema 和错误码。旧聊天请求若未传能力 ID，可在过渡期映射到聊天能力 ID 1，并在契约中注明兼容策略。
- 在 capability-service 增加内部只读能力详情接口，返回受控 code、状态、Schema 和单价；不向公开市场暴露服务内网地址、凭据和未上架能力。
- 执行器只能由服务端代码 allowlist 选择，不能让用户输入服务地址，也不能从数据库任意拼接 URL。
- 统一权限错误建议 HTTP 403 + 1007，或由 D2 契约评审确认平台兼容码。禁止各服务使用互相冲突的错误含义。
- API Key exchange 使用 POST，精确加入 Gateway 登录白名单，设置合理限流，不缓存响应，避免在 URL/访问日志中泄露 secret；JWT TTL 配置必须有硬上限。
- 管理写操作和全局统计实时向 user-service 校验当前角色/账号状态；无法核验时失败关闭。JWT role 可以帮助前端显示导航，但不能替代后端权限检查。
- 本期沿用现有多服务事务与幂等语义，不声称数据库之间有分布式原子事务。模型调用后若发生网络/计费失败，使用同一 requestId 幂等重试并登记对账风险；余额不足的明确预检分支必须在调用模型前拒绝。

### 5.2 模块依赖顺序

**角色和调用契约冻结 → user-service 的角色/Key/授权 → Gateway 可信身份 → capability-service 能力详情/Schema/价格 → ai-chat 受控 adapter → billing 能力 ID/积分流水 → 市场、Chat、设置、运营页面 → 全链路验收。**

前端只访问 Gateway 的 /api/**；微服务间使用 Python 基座的 call_internal 访问 /internal/**；不得跨库查询。各模块保持 API → Service → Repository → Model/Schema 的单向职责边界。

## 七、分模块详细任务

### 7.1 黄禹菲：user-service、billing-service、Settings UI

**user-service**

- 用户角色字段/枚举默认为 user；本地演示管理员只通过受控测试数据建立，不提供注册时选择角色或公开提权接口。
- 新增短期 Token 兑换接口，校验 access key、secret 摘要、Key 状态/过期时间、账号状态；错误凭证不透露 Key 是否存在或属于谁。
- 为跨服务管理授权提供只读 internal 检查，返回当前用户状态与角色；调用需校验可信透传用户和 requestId。
- Key secret 创建时返回一次；列表接口不回传 secret/hash；换取接口不记录请求体敏感字段。
- 更新 user-service 契约、前端类型、可重复增量 migration 和旧库升级核验步骤。
- 测试注册默认普通用户、有效/错误/禁用/过期 Key、用户禁用、角色降权、伪造请求头和 token TTL 上限。

**billing-service**

- 账单明细准确存储 capability_id、service_name、cost、status、duration 和 requestId；验证价格只能来自已校验的能力调用参数。
- 保持本地幂等明细、user 扣分、日聚合和回滚顺序；重复相同 requestId 返回首笔结果，不再扣积分。
- 全局 overview 限管理员，records/usage 只看当前用户；user-service 无法授权时拒绝全局统计。
- 测试不足积分、重复/冲突 payload、下游超时、禁用用户、回滚和幂等重试；明确本期不是跨库分布式事务。

**Settings 页面**

- 将 Key 生命周期和 Profile/Points 职责拆成小组件；展示 Key 创建成功后的“一次性复制”说明，不持久化 secret 到 localStorage。
- 展示访问 Token 兑换说明与过期提示，普通用户不能看到管理员入口。

### 7.2 夏思凯：capability-service、市场和运营界面

- 新增服务间只读接口 GET /internal/capability/{capability_id}，返回受控 code、status、param_schema、price_per_call；不把内部 service/path、密钥暴露给公开市场。
- 不存在、软删除、draft/offline 和暂不支持能力用一致错误语义处理，不泄露未上架项目详情。
- 分类/能力创建、修改、上下架、manage 列表均加当前管理员校验；授权依赖不可用时失败关闭。
- 对聊天和摘要的 seed、Schema、code、价格和前端输入统一；视觉能力保持草稿/不可体验。
- 市场卡片增加“体验此能力”入口及费用展示；Console 显示管理员可操作态，非 admin 显示服务端拒绝反馈。
- 覆盖内部详情、market 字段最小化、未授权管理、状态切换、错误参数和重复名称/编码等 pytest。

### 7.3 黄岑果：Gateway、ai-chat-service、Chat UI、CI/E2E

- Gateway 验证签名 JWT，丢弃请求方伪造的 X-User-ID、X-User-Name、role 和 requestId，再注入可信身份；仅精确放行原公开接口和 Key exchange；外部 /internal/** 仍一律拒绝。
- JWT 中 role 只用于导航/展示。所有 admin API 由业务服务使用实时 user-service 授权结果。
- 将能力详情客户端、输入 Schema/allowlist 校验、模型 adapter 与 chat orchestration 分开，避免在长业务 Service 内继续混入所有职责。
- AI 调用前验证 online/支持的 code/Schema，再按目录价格查询用户积分；条件不满足时确认模型客户端调用数为 0。
- 聊天使用既有会话服务；文本摘要使用单独 adapter 和准确参数映射，不能只改市场名称却调用不兼容 payload。
- 计量上报 capability_id、真实单价、同一个 requestId、user_id、模型状态和 duration；模型故障按原契约降级并不收费；Mock 不得访问外部模型。
- Chat UI 从市场选项获得 capability ID，显示 Schema 表单、实际价格、调用状态和追踪 ID；不接受用户传任意目标 URL。
- 统一前后端错误处理、E2E 脚本、README 和 Compose/init 副本同步方式；明确已有 MySQL 数据卷升级，不只更新首次初始化文件。

## 九、风险和控制措施

| 风险 | 影响 | 控制办法 |
|---|---|---|
| 角色、字段和费用口径跨服务不一致 | 集成返工 | D2 冻结契约；先做请求样例/接口测试；变更必须同步 PR |
| 旧 MySQL 卷不重跑 init SQL | 已有环境缺角色字段 | 单独写增量 migration 与核验说明；不删卷解决问题 |
| JWT 角色过期导致权限未及时撤回 | 越权管理 | 敏感 API 实时查询 user-service；下游异常时拒绝 |
| 任意 service/path 代理 | SSRF 或未授权服务执行 | 使用代码 allowlist；不接受用户 URL；不支持能力不执行 |
| 跨库调用无法形成分布式事务 | 模型成功但计费网络故障 | 稳定幂等键、回滚、重试、按 requestId 对账；文档标注一致性边界 |
| Key 或 Token 泄露 | 账号滥用 | 摘要存储、一次性显示、短 JWT、限流、日志脱敏、负例测试 |
| 真实模型不可用/意外费用 | 演示失败 | Mock 默认；真实模型可选配置，设置 timeout/token 上限和降级 |
| 页面价格与扣分对不上 | 演示不可信 | 同一能力详情来源；端到端比对 UI 价格、billing cost 和 user 余额 |
| 临时加需求挤占集成时间 | 不能交付 | 固定 P0，新增需求等量替换，经三人确认 |
| 公开演示凭据用于部署 | 安全隐患 | README 区分本地与部署配置；部署前禁用演示账号并更换密钥 |

**D8 摘要决策：** 若摘要缺少 Schema、adapter、计费或 E2E 任一验收证据，则摘要降为 P1，优先保证 Chat、角色、Key 安全、计费和迁移完成。不允许用静态假回复或错误 Schema 来宣称功能完成。
