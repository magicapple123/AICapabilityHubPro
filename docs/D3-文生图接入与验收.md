## 0. 为什么是 DashScope（而不是 `/v1/images/generations`）

需求原文写的是「上游 `/v1/images/generations`」，但实测 DeepSeek 账号在该路径返回 404；
DashScope 的文生图是**异步任务**（提交 → 轮询），所以实现里单列了 `dashscope-image` 协议：
`POST {base_url}/api/v1/services/aigc/text2image/image-synthesis`（带 `X-DashScope-Async: enable`），
再轮询 `GET {base_url}/api/v1/tasks/{task_id}` 直到 `SUCCEEDED`。
`openai-image` 协议仍保留，给兼容 OpenAI 图片接口的供应商用。

## 1. 前置条件（三项，缺一不可）

| 项 | 说明 | 配置位置 |
|---|---|---|
| `DASHSCOPE_API_KEY` | 阿里云百炼控制台申请，形如 `sk-xxxx` | 只在创建供应商时录入，**不写进任何 .env** |
| `PROVIDER_ALLOWED_HOSTS` | 必须包含 `dashscope.aliyuncs.com`，否则保存供应商会被拒（D1 的白名单） | `services/ai-chat-service/.env` 或容器环境变量 |
| `PROVIDER_MASTER_KEY_V1` | 32 字节随机数的 base64，用于加密落库的 Key；未配置时供应商功能失败关闭 | 同上，生成命令见下 |

```bash
# 生成主密钥（32 字节 → base64）
python -c "import os,base64;print(base64.b64encode(os.urandom(32)).decode())"

# 追加白名单（逗号分隔，保留已有值）
PROVIDER_ALLOWED_HOSTS=api.deepseek.com,dashscope.aliyuncs.com
```

改完必须重启 `ai-chat-service`（配置在进程启动时读取）。

## 2. 创建供应商（管理员）

```bash
TOKEN=<opsdemo 的 JWT>
curl -s -X POST http://127.0.0.1:8080/api/chat/providers \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{
    "name": "DashScope 文生图",
    "alias": "dashscope-image",
    "protocol": "dashscope-image",
    "base_url": "https://dashscope.aliyuncs.com",
    "api_key": "sk-你的key",
    "default_model": "wanx-v1",
    "timeout_ms": 60000
  }'
```

要点：
- `base_url` 只写到域名，**不要**带 `/api/v1/...`（路径由执行器拼）；
- `protocol` 必须是 `dashscope-image`，否则执行器不会走轮询分支；
- 返回里只会有 `api_key_mask`，密文以 `v1:` 前缀入库（D1）。

保存后可在「控制台 → 模型服务」点「测试连接」验证（会真实发一次最小请求）。

## 3. 登记能力

界面路径：控制台 → 能力目录 → 登记新能力。关键字段：

| 字段 | 值 |
|---|---|
| 能力编码 | `text-to-image`（必须与执行器注册的 code 完全一致，填错会提示「暂无执行器」） |
| 每次调用积分 | 建议 20（按次）或按件 1（`billing_mode=per_unit`） |
| 服务名 / 调用路径 | `ai-chat-service` / `/api/chat/completions`（仅展示用，实际由受控执行器决定） |
| 初始状态 | 先 `draft`，验收通过再改 `online`，勾选 `exposed_to_market` |

参数 Schema（直接粘进「输入 Schema」）：

```json
{"type":"object","required":["prompt"],"additionalProperties":false,
 "properties":{
   "prompt":{"type":"string","minLength":1,"maxLength":2000},
   "size":{"type":"string","enum":["1024*1024","1280*720","720*1280"],"default":"1024*1024"},
   "n":{"type":"integer","minimum":1,"maximum":4,"default":1}
 }}
```

## 4. 绑定供应商

能力的 `provider_alias` 指向第 2 步的 `alias`（`dashscope-image`）。绑定关系在
`t_capability.provider_alias`，也可在能力编辑页的「模型服务」下拉里选。

> 绑定不匹配（例如把 `image-generate` 绑到 `openai-chat` 的供应商）会在保存阶段被拒，
> 这是 D2 的校验，不是 bug。

## 5. 验收调用

```bash
SK=<你的 API Key 的 secret 部分>
curl -s -X POST http://127.0.0.1:8080/api/chat/completions \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"capability_id":<新能力 id>,"input":{"prompt":"一只戴宇航头盔的柴犬，赛博朋克风","size":"1024*1024","n":1}}'
```

期望：`data.images` 是非空数组，元素含 `url`（DashScope 的 OSS 临时地址）。

> 注（本轮修复的真实缺陷）：首次真实调用在出图成功后仍返回 `4003 系统内部错误`。
> 根因是 `services/billing-service/app/service/billing_service.py` 把
> `payload.images`（`list[BillingImage]`）直接写进 `t_call_record.images`（MySQL JSON 列），
> flush 时 `json.dumps` 抛 `TypeError: Object of type BillingImage is not JSON serializable`。
> 修复：落库前统一转成纯 dict（`images_for_storage()`），读回路径保持 `list[dict]`；
> 回归用例 `tests/test_billing_images.py`（纯内存转换 + 连库写入/读回各一条）。

## 7. 常见失败与定位

| 现象 | 大概率原因 | 处置 |
|---|---|---|
| 保存供应商报「host xxx is not in PROVIDER_ALLOWED_HOSTS」 | 白名单没加域名，或改了没重启 | 按 §1 配置并重启 ai-chat |
| 保存供应商报「must use https」 | 用了 http | DashScope 必须 https |
| 调用返回 5004 | 上游 401/402（Key 无效或欠费） | 换 Key / 充值；日志里 `status=401` |
| 调用返回 5003 | 上游 429 限流 | 降并发或提额 |
| 调用返回 5005 | 上游 5xx 或超时 | 看 `image_client` 日志里的 status；超时会重试一次 |
| 返回 `code=0` 但 `images` 为空 | 任务 `FAILED`（内容审核/参数非法） | 换 prompt 或 size，看 `task_status` |
| 前端没图 | 能力没绑对执行器 | 编辑页确认执行器提示为「该能力编码已有执行器」 |
