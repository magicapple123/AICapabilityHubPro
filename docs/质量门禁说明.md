# Pro 项目质量门禁说明

## 目的

质量门禁用于保证三位成员并行开发时，公共接口、服务边界、环境模板、构建和基础测试不被无意破坏。它不替代成员对业务功能、SQL、接口契约和端到端场景的实现与验收。

## 本地运行

在项目根目录运行：

```powershell
Set-Location D:\AICapabilityHubPro
python scripts/contract_lint.py
.\scripts\Assert-ProjectBaseline.ps1
.\scripts\Invoke-QualityGate.ps1 -SkipDocker -ReportPath artifacts\quality-gate.json
```

Docker Desktop 运行且需要检查 Compose 配置时，去掉 `-SkipDocker`。报告目录 `artifacts/` 只作为本地结果目录，不应提交。

## 当前门禁内容

- 检查四份接口契约是否存在并包含统一 Result 字段和 `/internal/` 边界。
- 检查各服务和部署目录的 `.env.example` 是否存在。
- 检查服务代码是否出现其它服务数据库名，防止跨库读取。
- 检查工作区是否出现不应提交的本地密钥/凭据文件。
- 检查 Pro 来源远端和 push 保护，避免把升级提交推回原项目。
- 运行 Gateway Maven 测试、四个 Python 服务 pytest/import、Web lint/build。
- 本地质量门禁将数据库连接目标固定到不可连接的 localhost 端口，让会清理 `qa*` 测试数据的数据库用例安全地按原测试夹具跳过；它不会连接服务 `.env` 中的 MySQL。实际数据库测试由 CI 一次性 MySQL 容器执行。
- 可选检查 `docker compose config`；Docker daemon 未启动时该步骤会失败，但不会影响其它本地单测结果。
- GitHub Actions 为每个 Python 服务启动一个临时 MySQL 8.4 容器，只导入该服务自己的 `sql/` 测试数据，再执行数据库行为测试；临时容器退出后数据销毁，不接触任何成员本地数据库。Gateway 使用 JDK 21，Web 使用 Node 24 与 pnpm 11。

## 基线限制

本地数据库集成测试依赖 MySQL；若本机 MySQL 未运行，pytest 会按原测试夹具报告 skipped。`skipped` 不等于数据库集成通过。可以在隔离测试库上复跑；不要把含用户数据的业务数据库直接当作自动化测试库。GitHub Actions 使用一次性隔离容器，提供 CI 数据库覆盖。若把项目复制到 D 槽原目录不存在的机器，来源隔离检查会标为跳过，其他检查仍会运行。

## GitHub Actions

`.github/workflows/quality-gate.yml` 将 Gateway、Python 服务、Web 和共享仓库检查拆成独立任务，便于定位失败原因。工作流不会写入真实环境变量，也不启动本地用户数据数据库。
