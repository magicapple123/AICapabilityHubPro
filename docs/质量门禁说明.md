# Pro 项目质量门禁说明

## 目的

质量门禁用于保证三位成员并行开发时，公共接口、服务边界、环境模板、构建和基础测试不被无意破坏。它不替代成员对业务功能、SQL、接口契约和端到端场景的实现与验收。

## 本地运行

在项目根目录运行：

```powershell
Set-Location D:\AICapabilityHubPro
python scripts/init_dev.py --install
python scripts/smoke_check.py --help
python scripts/contract_lint.py
.\scripts\Assert-ProjectBaseline.ps1
.\scripts\Invoke-QualityGate.ps1 -SkipWebInstall
```

首次 `init_dev.py --install` 会建立被忽略的本地 `.env`、服务专属 Python venv 和 Web 依赖；配置重复初始化测试验证原文件保持不变。默认静态检查 Compose（`config --quiet`）无需 Docker daemon，也不输出展开配置。`-SkipDocker` 可跳过静态检查。每次在 `artifacts/quality/<唯一编号>/` 创建汇总及 JUnit；已有指定报告会拒绝覆盖。`artifacts/` 已被 Git 忽略。

## 当前门禁内容

- 检查四份接口契约是否存在并包含统一 Result 字段和 `/internal/` 边界。
- 检查各服务和部署目录的 `.env.example` 是否存在。
- 检查服务代码是否出现其它服务数据库名，防止跨库读取。
- 通过 `git ls-files` 检查跟踪、暂存和可提交的未跟踪文件是否包含密钥/凭据；允许被 Git 忽略的本地 `.env`，不遍历虚拟环境或 node_modules。
- 检查 Pro 来源远端和 push 保护，避免把升级提交推回原项目。
- 运行 Gateway Maven 测试、四个 Python 服务 pytest/import、Web lint/build。
- 运行公共工具测试，验证首次配置生成、不覆盖、密钥一致、CI 报告判定与 HTTP 检查。
- 本地质量门禁将数据库连接目标固定到不可连接的 localhost 端口，让会清理 `qa*` 测试数据的数据库用例安全地按原测试夹具跳过；它不会连接服务 `.env` 中的 MySQL。实际数据库测试由 CI 一次性 MySQL 容器执行。
- `scripts/smoke_check.py` 是独立只读 HTTP 检查；显式运行才访问网关，默认门禁不需要服务已启动。
- 可选静态检查 `docker compose config --quiet`；中间件启动和健康联调独立检查。
- GitHub Actions 为每个 Python 服务启动临时 MySQL 8.4，只导入该服务 `sql/01_init.sql`，再执行完整测试。JUnit 必须有已执行用例、零跳过、零失败；报告作为 CI artifact 保留 14 天。该流程不接触成员本地数据库。

## 基线限制

本地数据库集成测试依赖 MySQL；若本机 MySQL 未运行，pytest 会按原测试夹具报告 skipped。`skipped` 不等于数据库集成通过。可以在隔离测试库上复跑；不要把含用户数据的业务数据库直接当作自动化测试库。GitHub Actions 使用一次性隔离容器，提供 CI 数据库覆盖。若把项目复制到 D 槽原目录不存在的机器，来源隔离检查会标为跳过，其他检查仍会运行。

## GitHub Actions

`.github/workflows/quality-gate.yml` 将 Gateway、Python 服务、Web、共享仓库和 Windows 公共工具拆成独立任务。Gateway 使用 JDK 21，Python 使用 3.12，Web 使用 Node 24 与 pnpm 11；Windows 任务另查 PowerShell 语法和可搬移的基线检查。`main`/`develop` 要求上述 8 个 check context 全部通过。
