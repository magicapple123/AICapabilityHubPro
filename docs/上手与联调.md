# Pro 本地上手与联调

## 开发入口

仓库为 `magicapple123/AICapabilityHubPro`，从最新 `develop` 建个人分支。原 `AICapabilityHub` 的内容和全部旧分支保留，Pro 的 `source` 本地远端禁止推送。

```powershell
Set-Location D:\AICapabilityHubPro
git switch develop
git pull --ff-only origin develop
git switch -c feature/自己的任务
```

当前已经复制旧项目的可运行代码。管理员、Key 兑换、Schema/按能力调用等 Pro 功能尚由三位成员按任务槽位实现，不能把旧接口存在当作这些新功能已经交付。

## 首次配置和依赖

确保 Python 3.12、JDK 21、Maven、Node 24、pnpm 及 Docker Desktop 已安装，然后运行：

```powershell
python scripts/init_dev.py --install
.\scripts\Test-ProEnvironment.ps1
```

初始化创建根 `.env`、`deploy/.env`、`web/.env`、四个服务的 `.env`，并建立各服务独立 `.venv`。网关与 user-service 使用一致的随机签名密钥，各服务数据库连接与 Compose 密码一致。生成的配置不会输出密钥，也不会被 Git 提交。

重复运行保留所有已有文件。如果根配置与现有 user/deploy 配置冲突，工具会在写入前拒绝，须在本地检查一致性，不能通过删配置或删数据卷来修复。只想生成配置而不安装依赖时，省略 `--install`。

## 启动顺序

Docker Desktop 运行后，启动独立的 Pro 中间件：

```powershell
python scripts/start_dev.py middleware
```

它只启动 MySQL、Nacos 和 Sentinel，不修改已有数据库、不执行升级 SQL。新数据卷首次创建时会按 `deploy/mysql/init/` 初始化旧版业务表和演示数据。

为下列组件各打开一个终端，工作目录均为 Pro 根目录：

```powershell
python scripts/start_dev.py gateway
python scripts/start_dev.py user-service
python scripts/start_dev.py capability-service
python scripts/start_dev.py billing-service
python scripts/start_dev.py ai-chat-service
python scripts/start_dev.py web
```

组件在当前终端运行，Ctrl+C 结束该进程；启动脚本不新开窗口，也不结束其它进程。端口已占用时拒绝启动，不自动改端口来隐藏问题。Web 默认真实登录，公开演示账号 `demo / demo123456` 仅适用于本地测试。

## 原项目的数据隔离

| 资源 | Pro 名称 |
|---|---|
| Compose project | `aicapabilityhubpro` |
| MySQL container | `aihub-pro-mysql` |
| Nacos container | `aihub-pro-nacos` |
| Sentinel container | `aihub-pro-sentinel` |
| Nginx container | `aihub-pro-nginx` |
| MySQL volume | `aihub-pro-mysql-data` |

Pro 不挂载原 `aihub-mysql-data`。主机端口仍按原课程约定使用 3306、8848/9848、8858、8080/8081/8082/8083/8090、5173；两套项目同时运行时会冲突，需人工选择停哪套或成组调整配置。

已有业务数据需要升级时，先保存备份，再由负责对应服务的成员提供增量迁移与验证。首次初始化脚本不修改已存在的表结构；seed 的 upsert 会改写示例数据，也不等同于迁移。禁止用删除数据卷来替代升级。

## 只读联调检查

全部服务注册到 Nacos 后运行：

```powershell
python scripts/smoke_check.py
# 自定义网关时
python scripts/smoke_check.py --gateway http://127.0.0.1:8080 --timeout 8
```

检查公开市场、未登录资料访问、普通及服务发现路径的 internal 隔离，以及经网关的四个服务 health。所有请求为无凭证 GET，不创建用户、不调用模型、不扣积分。失败时会显示具体路径；健康检查失败通常需检查服务注册，不能用直连服务替代网关链路通过。

## 自动验证和报告

```powershell
python -m pytest tests/tooling -q
.\scripts\Invoke-QualityGate.ps1 -SkipWebInstall
```

每次质量门禁使用唯一 `artifacts/quality/<编号>/` 保存汇总和 JUnit。使用 `-ReportPath` 指定文件时，已有报告会被拒绝覆盖。离线模式不会连接成员 `.env` 中的业务库，原数据库夹具的 skipped 会明确记录为未执行；CI 使用隔离 MySQL，并拒绝 skipped、0 个用例和失败的报告。

代码评审需要链接相同提交的 CI 报告；旧基线测试成功不代表 Pro 新功能测试成功。成员功能的验收矩阵见 `docs/验收用例.md`。

## 常见问题

- Docker daemon 未启动：打开 Docker Desktop 后重跑中间件启动命令，工具不会自行更改系统服务。
- 端口占用：检查原项目是否仍在运行；工具保留已有进程和数据。
- 登录成功但后续 401：确认网关和 user-service 使用同一 JWT 密钥/issuer；确认未显式开启占位登录。
- MySQL 密码不一致：核对根、deploy 与各服务配置；已存在数据卷的密码不会因改 `.env` 而自动改变。
- 配置已生成但门禁失败：查看报告的失败步骤；不得将生成的真实 `.env` 添加到 Git。
