## 本机运行

先按 `docs/双项目并行联调.md` 初始化并启动 Pro MySQL 3307、Nacos 8849/9849、Sentinel 8859，以及 user/capability/billing。已运行的组件不要重复启动。

首次获取本轮改动后，为 AI 服务补装新的 Schema 依赖，为前端安装锁定依赖：

```powershell
.\services\ai-chat-service\.venv\Scripts\python.exe -m pip install -r services/ai-chat-service/requirements.txt
pnpm --dir web install --frozen-lockfile
```

在三个独立终端中启动组长组件：

```powershell
python scripts/start_leader_dev.py ai-chat-service --catalog-mode market
python scripts/start_leader_dev.py gateway
python scripts/start_leader_dev.py web
```

`market` 是内部目录接口尚未交接时的显式兼容选择，只查询现有已上架详情。未显式选择时默认为 `internal`；依赖缺失返回 4002，不自动换成兼容路径。两种模式都验证能力状态、受控 code、Schema 和目录价格，不信任浏览器单价，也不根据数据库服务地址执行任意目标。

现有 `.env` 保留，入口只给子进程注入参数。真实登录仍为默认；本机公开演示账号 `demo / demo123456`。在本地 Mock 模式下，聊天返回模拟话术，摘要按输入生成截取摘要，响应明确 `mock=true`；这不代表外部模型供应商已经验收。

## 六分钟演示顺序

1. 登录并打开 `/chat?capability_id=1`。展示“多轮对话”、目录 5 积分及消息 Schema。
2. 输入一条消息。核对执行状态、实际 5 积分、账单编号、耗时和 requestId，随后去调用记录/积分页面核对相同 requestId。
3. 在能力选择框切换“长文本摘要”，或打开 `/chat?capability_id=2`。展示独立文本字段与目录 3 积分，提交自己的材料，核对输入相关摘要、3 分账单与追踪。
4. 查看历史会话，演示只有自己能访问；切换能力会重置输入上下文。摘要每次保存独立会话。
5. 以 `demopoor / demo123456` 登录，展示积分不足拒绝；不要用演示主账号去模拟余额不足。未知、草稿、Schema 不匹配和未实现执行器的自动化负例见 E2E。
6. 展示测试报告和“内部接口未交接时失败关闭”结果，说明 `market` 兼容模式与完整内部契约验收的区别。真实模型超时/坏响应的零收费由本地 HTTP 模型替身注入并自动核对，不依赖现场断网。

10/20用户授权的全站前端调整已接通市场到 `/chat?capability_id=<id>`，同时提供参数预览、执行器状态和设置页签。见[改版与验收](前端改版与验收-2026-10-20.md)。内部目录与实时授权仍需成员交付。

## 测试与证据

```powershell
# 网关测试并打包，供真实服务 E2E 启动
mvn -q -f gateway/pom.xml package

# 前端输入边界、lint/build
pnpm --dir web exec node --experimental-strip-types --test tests/chat-schema.test.ts
pnpm --dir web lint
pnpm --dir web build

# 浏览器只新增所需版本，保留已有浏览器缓存
pnpm --dir web exec playwright install chromium --no-remove

# 独立 MySQL + 独立服务进程/端口 + Nacos 专用 group + 本地模型 HTTP 替身
python scripts/run_leader_e2e.py --catalog-mode market --browser
```

运行前保证 Docker 引擎和 Nacos 正常、四个服务 `.venv` 依赖已安装。工具创建自己的命名数据库卷，不连接开发数据库；将测试 MySQL 的时间偏移与运行应用的主机对齐，避免 Windows 北京时间和 Ubuntu UTC 的日期边界差异。测试后停止其创建的进程和 MySQL，保留容器、数据卷与全部日志。它不删除旧项目或其它容器，也不重复使用以前的成功报告。

证据在唯一 `artifacts/leader-e2e/<编号>/`，包括：

- `summary.json`：四真实服务与 Gateway 的闭环结果、目录模式、内部接口是否实际验证。
- `browser/browser-summary.json` 和桌面/手机 PNG：UI 实际调用、收据、不可体验能力、错误态、移动布局与浏览器异常。
- 每服务日志、`browser-driver.log`、`resources.json`：故障复查与保留的测试资源名称，不输出 Token 或数据库凭证。

E2E 校验目录价、实际 cost、积分流水、余额变化与 requestId 一致；覆盖身份伪造、下架/不存在、未知执行器、错误 Schema、余额不足、模型 5001/5002 零收费、会话越权和 internal 路径隔离。业务服务、Gateway、MySQL 都是真实运行；外部模型端是明确标记的本地 HTTP 测试替身。

默认内部模式的客户端和失败关闭已实现。只有 `summary.json` 中 `member_internal_contract_verified=true` 才可称完整内部详情链已通过；市场兼容链通过不等于这个字段为 true。待内部接口交接后运行：

```powershell
python scripts/run_leader_e2e.py --catalog-mode internal --browser
```

ai-chat pytest 必须连接单独验收数据库并生成 JUnit，再用 `scripts/check_test_report.py` 严格检查；不要直接在开发 `.env` 数据库上跑会清理 qa 行的夹具。CI 的四服务矩阵为每服务提供隔离 MySQL，并拒绝 skipped、空报告、失败/错误。
