## 0. 环境与门禁执行口径（固定，勿改）

本机实际运行环境与文档默认值不同，**门禁必须用下面这组参数执行**，否则会因连错库或误打真实模型而出现假红/假绿：

| 项 | 实测值 |
|---|---|
| 仓库 | `D:\AICapabilityHubPro`（分支 `main`） |
| Python | 每个服务独立 venv：`services/<svc>/.venv/Scripts/python.exe`（3.12），根目录无共享 venv |
| MySQL | `127.0.0.1:3307`（`.env` 里写的是 3306，实际实例在 3307；测试必须显式传 `DB_URL`） |
| 根密码 | 见各服务 `.env` 的 `DB_URL`，日志不复制 |
| 网关 | 8080 已监听（现网进程），单元测试用 `mvn -q -f gateway/pom.xml test`，不依赖该进程 |

**数据库测试必须带的环境变量**（四个服务一致）：

```bash
TEST_DB_ISOLATED=1 \
DB_URL="mysql+pymysql://root:<pwd>@127.0.0.1:3307/<svc>_db?charset=utf8mb4" \
USE_MOCK=true            # 仅 ai-chat 需要；否则 .env 的 USE_MOCK=false 会真调上游
./.venv/Scripts/python.exe -m pytest tests -q
```

> 为什么必须 `USE_MOCK=true`：`ai-chat-service/.env` 里 `USE_MOCK=false`，`tests/test_api.py::test_completion_persists_session_and_messages`
> 断言 `data["mock"] is True`，不覆盖该变量会真调 DeepSeek 并红。这是**既有环境口径问题，不是代码缺陷**，已在基线记录。

- `ModelReply` 改为：`content / call_status / model_name` + `prompt_tokens: int = 0` / `completion_tokens: int = 0` / `usage_source: "upstream"|"mock"|"missing"` + `error_code` / `mock`；`total_tokens` 为派生属性。**取消** 原 `token_count` 字段（原语义是"total 或字符数"，不可用于计费）。
- 归一化：`usage.prompt_tokens`/`usage.completion_tokens` 优先，缺失时回落 `usage.input_tokens`/`usage.output_tokens`（Responses 协议）；两者都无 → `(0,0,"missing")`。**禁止**再用字符数冒充 token。
- `usage_source="missing"` 时：`per_call` 能力照常按次计费（旧能力金额不变）；`per_token` 能力**失败关闭** → `5002`，不产生账单。
- `t_call_record` 新增：`prompt_tokens INT NOT NULL DEFAULT 0`、`completion_tokens INT NOT NULL DEFAULT 0`、`token_source VARCHAR(16) NOT NULL DEFAULT ''`。旧行为 0/0/''，不回填。
- `t_chat_message` 新增 `error_code INT NULL`（A1 失败标记用）。`token_count` 语义固定为 **total_tokens**。
- 收据 `BillingRecordRequest` 新增 `prompt_tokens`/`completion_tokens`/`token_source`；`BillingRecordOut` 与 `CallRecordOut` 同步暴露。

**C2 双轨计费**
- `t_capability` 新增：`billing_mode VARCHAR(16) NOT NULL DEFAULT 'per_call'`、`price_per_1k_input INT NOT NULL DEFAULT 0`、`price_per_1k_output INT NOT NULL DEFAULT 0`、`price_per_unit INT NOT NULL DEFAULT 0`、`unit VARCHAR(16) NOT NULL DEFAULT ''`。旧两行保持 `per_call`，`price_per_call` 不动。
- 计价（整数，`ceil` 用 `-(-a//b)` 实现）：
  - `per_call`：`cost = price_per_call`
  - `per_token`：`cost = ceil((prompt*price_per_1k_input + completion*price_per_1k_output) / 1000)`；`total_tokens=0` → 0
  - `per_unit`：`cost = price_per_unit * units`（`units` 取请求 `n`，缺省 1）
  - 降级/失败一律 `cost = 0`（沿用既有语义）
- 预检门槛：`per_call` → `price_per_call`；`per_token` → `max(1, max(price_per_1k_input, price_per_1k_output))`（够 1k token）；`per_unit` → `price_per_unit * units`。
- 换算基准：**1000 tokens = 1 积分**，写入契约文档第 1 节。
- `CapabilityInternalOut` 增 `billing_mode`/`price_per_1k_input`/`price_per_1k_output`/`price_per_unit`/`unit`；`CapabilityMarketOut` 增 `billing_mode`/`unit`（列表与详情都加，`price_per_call` 保留不动）。
- `BillingRecordRequest` 新增 `billing_mode`/`units`；`validate_price` 改为按模式校验：`per_call` 保持 `points == unit_price`（旧行为），`per_token` 只要求 `points >= 0`，`per_unit` 要求 `points == unit_price * units`。
- `_is_same_call` 追加比较 `billing_mode`/`prompt_tokens`/`completion_tokens`/`units`。

**A1 事务边界**
- `complete()` 切三段：① 目录/预检/会话与用户消息 → `commit`；② 模型调用（**不持有连接**）；③ 新事务写助手消息 + 上报账单 → `commit`。
- 模型硬异常：③ 写一条 `call_status='failed'` 的占位助手消息（`error_code` 落库）后 `commit`，再抛 `4003`；用户消息保留。
- 账单失败：③ 回滚 → 助手消息与账单一起消失，用户消息保留（**语义变更**，旧测试 `test_billing_failure_rolls_back_messages` 需同步改为断言"会话=1、消息=1(user)"）。
- `completion_result()` 入参改为接收 `usage` 明细，不再由调用方算字符数。

**A2 连接池**
- 四服务 `db/session.py` 全部读环境变量：`DB_POOL_SIZE`(默认 5)、`DB_MAX_OVERFLOW`(默认 10)、`DB_POOL_TIMEOUT`(30)、`DB_POOL_RECYCLE`(1800)。
- worker：`UVICORN_WORKERS`（默认 1，生产 4）；容量公式 `4 服务 × 4 worker × 15 = 240`，故 MySQL `max_connections` 必须 ≥300。
- MySQL 侧：`deploy/mysql/conf.d/10-max-connections.cnf`（`max_connections=500`）+ compose 挂载；本地实例提供 `SET GLOBAL max_connections=500` 增量脚本。
