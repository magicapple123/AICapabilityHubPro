适用工作区：`D:\AICapabilityHubPro`。2026-10-19 已在保留原项目运行的情况下完成联调。

原项目中间件占用 3306、8848/9848、8858 时，使用本文的显式并行模式。原有 `scripts/start_dev.py` 仍适用于默认端口；本文模式由新增入口提供，不改写已有配置。

## 首次启动

已初始化过的机器不必重复安装。新机器先执行：

```powershell
Set-Location D:\AICapabilityHubPro
python scripts/init_dev.py --install
```

启动 Pro 中间件：

```powershell
python scripts/start_pro_local.py middleware
```

等待 MySQL 健康后，为以下六个组件分别打开终端，均在 Pro 根目录执行：

```powershell
python scripts/start_pro_local.py user-service
python scripts/start_pro_local.py capability-service
python scripts/start_pro_local.py billing-service
python scripts/start_pro_local.py ai-chat-service
python scripts/start_pro_local.py gateway
python scripts/start_pro_local.py web
```

上述六条命令各自持续运行，不能在同一个终端中顺序等待执行；前台启动时使用 Ctrl+C 结束对应组件。Nacos、网关启动和服务发现需要时间，待注册完成后再做 smoke 检查。

入口复用原启动工具，在子进程环境中统一设置 Nacos、Sentinel 和各服务的 Pro 数据库连接。MySQL 及 JWT 凭证取自已生成的根 `.env`；发现与 deploy/user 配置不一致时拒绝启动。既有 `.env` 不被改写，凭证不进入命令行输出。

不要混用两种入口：使用本模式启动中间件时，各应用也使用 `start_pro_local.py`，避免默认入口连接旧项目的 Nacos/MySQL。已经运行的组件不要再次启动，原工具会拒绝占用的应用端口。

## 数据库测试边界

数据库 pytest 含测试数据清理逻辑，必须连接独立验收实例，不能直接使用旧项目或 Pro 应用的数据库。本次实例为 `aihub-pro-qa-mysql-20261019-002600`，测试结束后已停止，容器和独立数据卷保留。

Windows 本机为北京时间，测试 MySQL 也须使用相同时间基准。新建验收实例时配置 `TZ=Asia/Shanghai`，启动后核对 MySQL 的 `NOW()` 与本机日期。GitHub Actions 中应用与数据库都为 UTC，属于另一套相互一致的环境。

本次首次验收实例遗漏 TZ，出现 UTC 的 10 月 18 日与本机 10 月 19 日错位，billing 的四个当天统计断言失败。仅在独立验收实例设置 `time_zone='+08:00'` 后，原封不动复跑四个服务测试，共 180 项通过，零跳过；失败与复测报告均保留。

后续重启该验收实例时，全局 `time_zone` 的临时设置可能恢复默认，必须重新核对；不要直接沿用旧报告。测试通过后继续用 `scripts/check_test_report.py` 严格检查 JUnit，不能用 `--allow-skips` 作为数据库验收证据。

详细结果见 [联调验收记录-2026-10-19.md](联调验收记录-2026-10-19.md)。本次完成公共运行环境和原业务基线验证，三位成员的 Pro 新功能仍按计划待实现。
